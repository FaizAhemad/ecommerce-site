GADGIFY PAGE-BY-PAGE REVIEW PLAN
================================

Purpose
-------
This file is the human-readable route index and review order requested by the owner.
APPLICATION_BACKLOG.md remains the only completion checklist. Completion evidence and
limitations belong in PROJECT_STATUS.md; current route behavior belongs in PAGE_INVENTORY.md.
Each route is reviewed in its own batch. After a page batch is presented, the owner revalidates
that page before the next page review begins.

Review standard for every page
------------------------------
Security first: route and API authorization, account/shop ownership, private data exposure,
CSRF, safe errors, input bounds, duplicate-write guards, untrusted content/media and no
optimistic payment/order outcomes. Then review field validation and wording, keyboard/accessibility,
loading/refresh/empty/error/pending/success states, and layout at 320, 360, 390, 430, 768, 1280
and 1440 CSS pixels. Use synthetic records only. Playwright must run against local Vite with
mocked API responses; never point write tests at production or a live database/provider.

------------
01. Home: / — startup into the landing page, hero, navigation, categories, featured/new products,
    product cards, add-to-cart feedback and newsletter validation/confirmation states.

    mobile filter drawer, cards and query state in the URL. Specific mobile loading checkpoint:
    capture the delayed initial-load skeleton and verify it stays two columns at 320/360/390/430px,
    matching loaded product cards; compare loading and loaded screenshots before moving on.
    Filter scenarios: verify the default query has no active search/category/color/rating/cursor filters, then exercise category-only, color-only and rating-only cases to ensure unselected facets stay omitted;

Navigation and identity policy to validate
------------------------------------------
Guest: Home, Products, Shops, Sell with us, Support, search, Cart and Sign in. Hide private
Orders, Profile and Admin destinations. Seller entry is a public application entry, not seller data.
Signed-in customer: public links plus Orders, Profile and Seller workspace; the seller workspace
entry is visible to all signed-in users and is an apply/manage destination. Admin: the server-
assigned ADMIN role adds Admin; never infer it from email/name. Admin also sees Orders, Profile
and Seller workspace because the current shared layout gates those links on authentication.
Seller actions/data still require current server-verified shop membership and status. Staff: there
is currently no staff role/permission model; do not show staff links or create a staff login until
scoped permissions are designed and enforced server-side.
Use one credential/sign-in flow with role-aware redirect/navigation. Separate login pages would
not provide security and risk inconsistent authentication. Direct-route and API authorization
must be tested independently of navbar visibility.

Automation status
-----------------
Playwright config and the Home and Products specs live in playwright.config.ts, e2e/home.spec.ts
and e2e/products.spec.ts. Specs use local synthetic fixtures, block external network access,
exercise selected responsive and loading states, and avoid live writes. Add route/state coverage
during each page batch. Do not claim untested pages or real devices are verified.

Windows run sequence (Node 22 required by the repository)
----------------------------------------------------------
Set PLAYWRIGHT_BROWSERS_PATH to .playwright-browsers in PowerShell, then run
`npx playwright install chromium` once. In one terminal run `npm run dev`. In another terminal,
set the same PLAYWRIGHT_BROWSERS_PATH and run `npm run test:e2e:home` for Home or `npx playwright test e2e/products.spec.ts` for Products. Keep the local dev server
running until the test process exits; the configuration intentionally does not own server startup
because Windows child-process cleanup stalled here. API calls are mocked by the test and the runner
rejects non-loopback base URLs; never use production/customer credentials.
