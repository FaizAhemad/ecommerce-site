# Profile and saved addresses

/profile is common to signed-in customers and admins. Guests use the existing login form. The header Profile link replaces Account email; verification and email-based password recovery remain linked inside Profile. Admin Settings is store configuration and is unchanged.

GET /api/profile returns name, email, phone, verification booleans and selected owned addresses. PATCH /api/profile accepts name and phone; changing the login phone requires currentPassword. It checks account version/password hash at write time, clears phone verification and invalidates owner mobile tokens transactionally. Removing the only login contact is rejected. Email, role and owner identity cannot be changed through this API. Mobile verification, verified email replacement and passwordless-account phone-change workflows remain future work.

POST /api/addresses creates an address. PATCH accepts id plus full address fields, or id and makeDefault:true. DELETE accepts id. Ownership always comes from the session. The first address is default; selecting another clears the previous default. Deleting the default promotes the oldest remaining address. To stop an address being default, select another. Fields include label, recipient name, address lines, city, state, postalCode, two-letter country and optional phone. This is bounded generic validation, not a promise of deliverability or country-specific postal rules.

Addresses referenced by orders cannot be edited/deleted because orders currently reference the address row. Add a new address instead; default selection on an existing order address is allowed. Address changes run in Serializable transactions with no replay. No database uniqueness constraint or migration was added; other/future write paths must preserve the same invariant.

All writes use central CSRF, session-owned IDs, private/no-store responses, safe errors and profile-write quotas of 60/IP + 20/account per minute. Private query keys and session abort guards prevent old-account results from being applied. Customer data/passwords stay out of persistent browser storage and logs. Form drafts remain after failures; successful operations reconcile only from server responses. A timeout can leave a committed outcome: refresh before manually retrying.

All 129 offline tests, formatting and offline build/types pass; three existing lint warnings remain. No .env, live API/database/provider/browser checks, migration or deployment were performed. The owner validates phone changes and login, own/foreign address handling, defaults and order references, 429/offline/conflict behavior, account switch, and Android/iOS 320-430px focus/keyboard/layout. Full checkout integration, mobile verification, verified email replacement and localization remain pending. PROJECT_STATUS E19 holds evidence; APPLICATION_BACKLOG is the sole completion checklist.
