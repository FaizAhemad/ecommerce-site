# Commerce schema review and evolution plan

Source review: 2026-09-30. Read with REBRAND_IMPLEMENTATION_PLAN.md, PRODUCT_VARIANTS.md and existing marketplace/payment/refund contracts. APPLICATION_BACKLOG.md is the sole implementation checklist. This document proposes changes; schema.prisma and migrations were not changed or executed.

## Current foundation and review scope

Reviewed the complete `prisma/schema.prisma`, migration names/DDL constraints, cart coordinator and order creation, plus existing refund and notification persistence. The project declares Prisma/client `^6.12.0`; examples from newer major versions must not be applied without a separate upgrade decision.

The schema already covers users, hashed sessions and verification tokens, addresses, categories, products/media/colors/reviews, cart/wishlist, order/item snapshots, one payment and shipment per order, returns, support conversations/media, newsletter and marketplace ownership/fulfillment. PostgreSQL migrations also contain constraints absent from Prisma's model display: marketplace status checks, one platform shop, purchase-feedback bounds and compare-at-price checks. Inspect migration SQL before declaring a constraint missing.

Several real workflows use reserved StoreSetting keys rather than dedicated Prisma models: refund-attempt claims, order-email jobs, coupon usage, seller application/draft/media records, moderation and inspection/dispute data. They are implemented persistence, not nonexistent functionality. Extract them only with an explicit compatibility migration preserving version, ownership, claim and no-replay semantics. Prepared files do not establish applied production schema; owner rehearsal/acceptance is still required.

## Proposed relationship outline

Product -> ProductVariant -> chosen option values; Cart -> CartItem -> exact product/SKU; Order -> OrderItem -> immutable SKU/option/price snapshots. Order -> OrderAddressSnapshot. Order -> existing Payment summary -> many PaymentAttempts. InventoryMovement/Reservation reference exact sellable stock and source order line. SellerOrder and ShopOrderItem remain the authoritative shop grouping; a variant must never cross shop ownership.

For simple products choose one inventory authority during the SKU rollout. Recommended path: create a default SKU for each existing product, preserve current product identifiers/API compatibility temporarily, then migrate stock/price reads and writes together. Do not keep parent and SKU stock independently mutable. Alternative nullable variant lines need explicit database uniqueness and more conditional code; choose before authoring DDL. PRODUCT_VARIANTS.md's simple-product compatibility requirement still applies.

## Integrity and security requirements

Money remains integer minor units with currency; define range/rounding rules. Candidate database checks include nonnegative stock/price/charges, positive cart/order quantities and rating 1–5, after auditing existing migration constraints/data. Aggregate totals, allocation sums and transition legality often need transactional enforcement rather than a row CHECK. Decide compare-at clearing/rejection behavior when price changes; preserve the existing higher-than-price constraint.

Payment provider identifiers must be bound uniquely at the appropriate provider/account scope once existing duplicates/nulls are audited. An attempt is not a new customer order. Store sanitized failure codes/messages only; no card credentials or unrestricted provider payload. Order/payment/refund/fulfillment states are distinct concepts; do not rename enums merely for friendlier UI copy. Close/dismiss is not proof of bank failure; capture proof remains server/provider verified.

Retain minimal selected DTOs, account/shop scoping and verified identity. User.role already distinguishes CUSTOMER/ADMIN; ShopMembership is separate. No OWNER role or automatic elevation is needed to fix an admin display label. Administrative role assignment needs a privileged audited workflow, not public profile fields.

Use foreign keys and retention-aware deletion rules for new financial/audit records. Do not introduce user/product hard-delete paths that destroy order history. Review existing cascades and preservation/anonymization requirements with the owner before changing them. Standardize timestamps and version columns deliberately; SQL-driven writes to `@default(now())` updatedAt fields must explicitly update them where required.

Stock availability shown to users is advisory; checkout rechecks exact SKU stock in the serializable transaction. Reservation expiration must coordinate with pending/authorized/late-captured payments and cancellation. Do not enable a cleanup job that releases inventory blindly while a payment may still complete.

## Safe migration sequence

1. **SE-01 contract/integrity inventory:** map current Prisma, SQL-only constraints, reserved settings and prepared migrations; define versioned cart mutation/receipt behavior and historical snapshot contracts. Establish owner-provided applied-schema evidence without reading production here.
2. **SE-02 catalog content and SKU foundation:** add optional descriptive fields and additive SKU/option tables; prepare deterministic simple-product mapping and shop ownership checks. Keep existing products purchasable through a compatibility layer.
3. **SE-03 transactional integration:** migrate cart line identity, order snapshots, stock authority and admin/seller editors together. Include conflicting-tab mutations, checkout reservations, cancellation/restock and rollback fixtures.
4. **SE-04 payment/history:** retain Payment summary; add attempt records, provider identity uniqueness, address/adjustment snapshots and reconciliation. Never reissue a financial operation during backfill.
5. **SE-05 scale and lifecycle:** extract selected settings workflows to typed tables one at a time; add measured indexes/media metadata and optional item-level fulfillment/returns only with approved behavior.

For every migration: expand -> backfill -> validate -> switch readers/writers -> observe -> contract in a later release. Define compatibility and rollback before the switch. Backfill historical unknown values as explicitly unknown; do not synthesize past addresses, events, SKU choices or payment attempts. Preserve row counts, charge totals, foreign-key ownership and unique operational claims. Reconcile all in-flight jobs before moving stores; a copied job must never send/refund again because its storage key changed.

No migration, Prisma generation, environment read, provider operation or database check is authorized by this plan. Owner applies/rehearses changes and supplies evidence. Tests should use synthetic fixtures for old/new records, duplicate requests, concurrency, account/shop isolation and ambiguous payment outcomes. UI-only RB-01/RB-02 can proceed before schema work; rapid cart queuing depends on SE-01, real variant selection on SE-02/03, and richer payment-attempt displays on SE-04.

## Standards and sources

These are application design recommendations, not a universal ecommerce schema or certification. Preserve the installed Prisma major version and inspect version-specific documentation before generating migrations. [Prisma v6 introspection](https://docs.prisma.io/docs/orm/v6/prisma-schema/introspection) explains why database structure and the Prisma representation must be reconciled; [Prisma migration guidance](https://www.prisma.io/docs/guides/database/data-migration) informs staged evolution, not an instruction to upgrade this project. [Razorpay's published FreshToHome case study](https://razorpay.com/assets/case-studies/pdf/Razorpay_-_FreshToHome_Case_Study.pdf) illustrates associating payment attempts with an order; current provider API contracts still govern implementation. UI references and evidence limits are in REBRAND_IMPLEMENTATION_PLAN.md.
